# HTML 统一管理平台 · 架构方案

## 一、要解决的问题

公司鼓励各部门自己做 HTML 页面后，页面散落在各自的共享盘、网盘甚至个人电脑里。领导的要求是三件事：

1. **统一管理** —— 所有 HTML 收进一个平台，能按分类浏览、按关键词搜索，领导不用挨个部门问"你们那个页面在哪"
2. **分级访问** —— 部分内容只能内网看，部分内容可以对外
3. **强制收口** —— 以后新做的 HTML 都要交到平台上来

其中第 2 条是技术难点：它不是"加个登录判断"那么简单，一旦做错就是内容外泄事故。

---

## 二、为什么隔离要分三层做

很多系统只在应用层加一个 `if (isInternal && !loggedIn) throw 403`。这个做法的问题在于：**它假设所有请求都一定会经过应用代码**。一旦有人绕过应用直接访问存储层、或者代码里某个分支漏了判断，内容就出去了。

本方案采用三层叠加，**任意一层单独失效都仍然安全**：

```
员工浏览器 / 外网访客
        │
        ▼
┌───────────────────────────────────────────────┐
│ 防线 1 · 文件系统级隔离（最外层）                │
│ 外网容器只挂载 data/public                     │
│ internal/ 与 dept/ 在其文件系统中不存在          │
│ → 不是"被拦住"，是"文件不在这里"               │
└───────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────┐
│ 防线 2 · 应用层强制过滤                        │
│ 站点角色由「入口」决定（绑定地址 + 端口），       │
│ 请求头只作辅助、且视为不可信；                   │
│ 外网站点强制注入 visibility=public 且 status=  │
│ published，丢弃用户传入的任何过滤参数            │
│ 管理类接口在外网站点直接 404                    │
└───────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────┐
│ 防线 3 · 同源 XSS 沙箱                          │
│ 用户 HTML 运行在 CSP sandbox 产生的            │
│ 不透明源（origin=null）下，                     │
│ 无法读取本站 Cookie、DOM、localStorage          │
└───────────────────────────────────────────────┘
```

### 防线 1 的关键价值：消除对网络拓扑的依赖

最初的问题是：**公司内外网是怎么隔离的，我们不确定**。

如果依赖"内网域名只在内网 DNS 解析"，一旦内外网其实是同一套网络（靠防火墙规则区分），或者 DNS 配置有疏漏，防线就形同虚设。

所以本方案**不把网络隔离当作安全前提**。外网 Nginx 容器在 `docker-compose.yml` 里只挂载了 `./data/public`：

```yaml
web-external:
  volumes:
    - ./data/public:/srv:ro      # 只有这一个
```

对比内网容器：

```yaml
web-internal:
  volumes:
    - ./data:/srv:ro             # 全量
```

即使内外网真的共用同一个网段、外网流量能直接路由到这台机器，外网容器里也**没有** `internal/` 这个目录，Nginx 只会返回 404。网络隔离退化为锦上添花，不再是生死依赖。

> 这就是把一个"不确定的网络问题"转成了"确定的文件系统问题"。

### 防线 2 的前提：站点身份不能由请求头决定

三层设计里最容易踩的坑，是**站点角色怎么判定**。原实现直接采信 `Host` / `X-Forwarded-Host`，实测结果：

| 请求头 | `/api/manage/pages` | `/api/auth/site` 的 scope |
|---|---|---|
| `Host: www.公司域名`（正牌外网） | 404 | `public-only` |
| `Host: intranet.公司域名`（伪造） | **401**（存在性暴露 + 攻击面暴露） | **`full`** |
| `Host: 8.8.8.8`（随便一个 IP） | **401** | **`full`**（兜底到内网站点） |

也就是说：只要入口把客户端的 `Host` 原样透传给后端，外网就能"自称"内网，防线 2 名存实亡。修复分三处：

| 位置 | 措施 |
|---|---|
| nginx（生产入口） | `Host` / `X-Forwarded-Host` 写死为本站点域名，**不透传 `$host`**；并加 `default_server` 兜底块：Host 不匹配任何 `server_name` 时直接 `return 444` |
| vite（dev 入口） | 代理转发时把站点身份钉死为本实例入口（5173 恒内网 / 5174 恒外网），客户端写什么头都不影响 |
| 应用（最终兜底） | `config/sites.json` 的 `fallbackSiteId` 指向权限最小的 `external`：Host 认不出来时给公开站点，而不是 `scope=full` 的内网；`loadSitesConfig` 会拒绝把 `manageEnabled` 的站点设为兜底 |

**残留前提（代码管不了）**：API 端口（3000）与内容端口（4000/4001）必须只在内网/本机可达。直接打到 API 的请求仍然可以自称任意 Host——生产编排里 `api` 只 `expose` 不 `ports`，天然满足；自建/试验时**绝不能把这三个端口映射到公网**（见部署手册 3.8）。

## 三、目录布局

```
data/
├── public/{slug}/        外网公开页面          ← 外网容器可见
├── internal/{slug}/      仅内网全员            ← 外网容器不可见
├── dept/{slug}/          指定部门可见          ← 外网容器不可见
└── versions/{pageId}/{versionId}/   不可变版本快照
```

发布时的分发规则：

| 可见性 | 落地目录 | 外网容器能否读到 |
|---|---|---|
| 外网公开 | `public/{slug}` | 能 |
| 仅内网全员 | `internal/{slug}` | **不能** |
| 指定部门可见 | `dept/{slug}` | **不能** |

页面可见性或状态变更时触发同步：从旧目录删除、写入新目录、下线则三个目录全部清除。

`versions/` 只存历史快照，任何人都不会直接访问它，内容分发只从三个发布目录读取。

## 四、同源 XSS：一个容易被忽略但致命的问题

这是本方案里最需要向评审说明的一点。

员工上传的 HTML 里带 JavaScript。**如果管理后台和用户页面同源同域，员工上传的页面就可以直接带着管理员的登录 Cookie 去调用后台接口**：

```javascript
// 员工上传的 HTML 里这段代码
const data = await fetch('/api/manage/pages', { credentials: 'include' }).then(r => r.json())
// 页面列表、审核记录、上传人邮箱，全部拿走
```

等于给全公司开了一个后门。所以做了四件事：

| 措施 | 作用 |
|---|---|
| **域名分离** | 后台 `admin.corp.com` 与内容 `intranet.corp.com` 不同域。即使内容页能发请求，也不带后台 Cookie，且被 CORS 拦截 |
| **CSP sandbox 不给 `allow-same-origin`** | 页面运行在 `origin=null`，浏览器层面无法读取本站任何数据 |
| **不透明源挡请求** | 不透明源发出的请求 `Origin` 头为 `null`，后端 CORS 直接拒绝 |
| **后台 Cookie `HttpOnly`** | JS 读不到 Cookie 原文 |

**这里有个前置条件**：不给 `allow-same-origin` 会导致页面自身的 `localStorage` 失效。本方案在立项前确认了所有页面均为**纯静态展示**，不需要本地存储、不需要调用内部接口，因此这个最严格的档位可以零代价使用。

如果将来出现需要登录态或本地存储的页面，方案是：给该页面单独的二级子域，且不与后台共享 Cookie，单独在沙箱白名单里放行。

### 安全响应头

内容响应统一附加（见 `config/security-headers.json`）：

```
Content-Security-Policy: sandbox allow-scripts allow-forms allow-modals allow-popups allow-downloads;
  default-src 'none';
  script-src 'unsafe-inline' http: https: data: blob:;
  style-src 'unsafe-inline' http: https: data:;
  img-src http: https: data: blob:;
  font-src http: https: data:;
  media-src http: https: data: blob:;
  frame-src http: https:;
  connect-src 'none';
  object-src 'none'; base-uri 'none'; form-action 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
X-Frame-Options: DENY
```

策略是**「允许加载静态资源，禁止外传数据」**：

- `default-src 'none'` —— 没有显式列出的载体（worker、manifest 等新通道）默认全部拒绝，白名单之外零开口
- `script/style/img/font/media` 放开 `http: https:` —— 允许引用外部 CDN 与包内相对路径资源；
  这里必须写 scheme 而不是 `'self'`，因为页面在 CSP sandbox（无 `allow-same-origin`）下处于**不透明源**，
  `'self'` 对任何同宿主资源都匹配不到（dev 是 http，prod 是 https，所以两个都放行）
- `connect-src 'none'` —— 页面**不能发起 fetch/XHR/WebSocket/sendBeacon**，
  JS 没有把任何数据主动发出去的通道
- `sandbox` 不给 `allow-same-origin` —— 页面 `origin=null`，读不到 Cookie/localStorage/DOM，
  即使加载了外部资源，也无法携带平台凭据
- `'unsafe-inline'` 只出现在 script/style，页面中的内联脚本与样式可以工作

大于普通追踪像素风险的口子（如表单提交）也被 `form-action 'none'` 封死。

### 副作用：沙箱页面取不到自己的图片

`sandbox` 不给 `allow-same-origin`，页面就处在**不透明源**。浏览器做 `SameSite` 判定时，会把不透明源对
`/p/{slug}/images/x.png` 的子资源请求当成**跨站**请求，于是 `SameSite=Lax` 的登录 Cookie 不下发：

```
GET /p/{slug}/              200  ← 顶层导航，带 Cookie
GET /p/{slug}/images/a.png  401  ← 子资源，浏览器主动去掉了 Cookie
```

公开页面看不到这个现象（本来就不需要登录），所以很容易漏测——真实 Chrome + 真实会话才好复现。

**解法：页面级资源令牌，只给静态资源开口子，不给 HTML 开口子。**

```
点击打开 → GET /api/pages/{slug}/play
        → 302 /p/{slug}/_a/{令牌}/          ← 令牌写在路径里
        → 页面内 assets/a.png 相对路径自动继承
          → /p/{slug}/_a/{令牌}/assets/a.png
```

| 请求 | 校验什么 |
|---|---|
| `/p/{slug}/_a/{令牌}/` 下的 png/css/js/mp4… | 只校验令牌（HMAC + 7 天有效期），不要求 Cookie |
| `/p/{slug}/_a/{令牌}/` 本身、`*.html`、子目录 | **仍然要求登录 + 部门权限**，令牌在这里不起作用 |
| `/p/{slug}/images/a.png`（无令牌） | 仍然要求登录，原有行为不变 |

令牌算法：`{过期秒}.{base64url(HMAC-SHA256(secret, "asset\n{slug}\n{过期秒}"))}`。
dev 由 `scripts/serve-content.mjs` 校验，生产由 nginx 的 `auth_request → /api/guard/asset/:slug` 校验，
密钥为环境变量 `CONTENT_TOKEN_SECRET`（生产必填）。

**为什么不削弱隔离**：令牌绑定 slug，只能取这个页面的静态文件；HTML 一律仍要会话，
所以把带令牌的地址发给没有权限的人，对方打开只会得到 401/404。
文件系统隔离、站点过滤、部门权限三层都没有被绕过。

> 已否决的两条路：
> ① 把会话 Cookie 改成 `SameSite=None; Secure`——要求全站 HTTPS，而内网是 `http://10.x.x.x`（不可信源），
> Chrome 会直接拒收；而且它放宽的是**所有**请求的跨站策略，代价远大于收益。
> ② 去掉 `sandbox` / 加 `allow-same-origin`——等于把同源 XSS 防护拆掉，是本方案最不能碰的一层。

## 五、权限模型

### 三档可见性

| 可见性 | 谁能访问 | 发布需要审核 |
|---|---|---|
| 外网公开 | 任何人，无需登录 | 是 |
| 仅内网全员 | 任何登录用户（含 VPN 出差人员） | 是 |
| 指定部门可见 | 所选部门的登录用户 | 是 |

### 默认值策略：强制选择，不给默认

上传时可见性是**必选项**，没有默认值。

理由：安全默认值应该是最保守的那个，但"默认内网"会让员工觉得麻烦从而随手改成公开；而"强制选择"把决策责任放在人身上，同时在界面上写清每档的含义。这是有意的摩擦。

### 部门级可见的鉴权实现

`dept` 档位无法靠目录隔离（一个页面可能对多个部门可见，复制到每个部门目录会造成重复），改为**请求级鉴权**：

```
Nginx location /p/{slug}/
  └─ auth_request → GET /api/guard/content/{slug}
       ├─ 返回 204 → 放行
       ├─ 返回 401 → 需要登录
       ├─ 返回 403 → 无权限（不在授权部门）
       └─ 返回 404 → 页面不存在或未发布
```

判断逻辑集中在 API 一处，Nginx 只负责转发，子请求开销约 5ms。对百人规模完全够用。

### 内网也必须登录

原本的考虑是"内网免登录，出差员工走 VPN 也能直接看"。最终选择**内网也必须登录**，原因是：

- 鉴权逻辑统一到一个 `auth_request`，不必维护两套规则
- 出差人员通过 VPN 连上内网后同样能访问，体验不降级
- 登录态可以追溯到具体人，便于审计

## 六、审核与状态机

```
draft ──提交──▶ pending ──通过──▶ published ──下线──▶ draft
                    │                  │
                  驳回               删除
                    ▼                  ▼
                 rejected          回收站(30天)
```

删除不属于状态流转，而是独立的软删除标记 `deletedAt`：页面状态保持不变，但对所有人立即不可见，内容桶同步清除；30 天后由定时任务彻底删除记录与文件。

删除入口**只对未发布页面开放**（草稿、审核驳回），已发布页面必须先经下线流程变回草稿，避免绕过管理员审批直接下线。

两条重要的安全规则：

1. **修改已发布页面的可见性，会立即下线并回到 `pending`**。防止有人绕过审核把内网页面直接改成公开。
2. **上传新版本会把已发布页面打回 `draft`**。内容变了就要重新走审核，不能"改完直接沿用旧审批"。

## 七、数据模型

```
Department   部门          id · name · code · sortOrder
Category     业务分类      id · name · sortOrder
Tag          标签          id · name
User         账号          id · email · passwordHash · role · departmentId

Page         页面          id · slug · title · summary
                         visibility(public|internal|dept)
                         status(draft|pending|published|rejected)
                         deletedAt · deletedById（回收站）
                         packageType(single_file|bundle) · entryFile
                         currentVersionId · publishedVersionId
                         viewCount · lastViewedAt · publishedAt

PageVersion  版本          id · pageId · versionNo · storagePath · sizeBytes · changelog
                         ↑ 只读不可变；每次上传产生新版本
PageDept     部门授权      pageId · departmentId
PageTag      页面标签      pageId · tagId
ViewStat     按天统计      pageId · date · count
AuditLog     审计日志      userId · action · pageId · ip · ua · detail
```

两个设计要点：

- **`currentVersionId` 与 `publishedVersionId` 分离**。前者是"最新上传的版本"，后者是"线上正在跑的版本"。上传新版本只动前者，审核通过才动后者。这样"已发布页面有未审核的新草稿"是天然支持的状态。
- **页面与版本分表**。版本记录只增不改，天然支持回滚与审计追溯。

### 账号字段的可变更矩阵（已定规则）

| 字段 | 本人 | 管理员 | 理由 |
|---|---|---|---|
| password 密码 | ✅ 可改（POST /api/auth/password，需当前密码，新密码 ≥8 位） | ✅ 可重置（用户管理，服务端生成一次性密码） | 改密会自增 `sessionVersion` 并给当前端换发新 cookie：其它设备上的旧会话立即失效，自己不被踢下线。旧密码错回 400 而非 401，避免前端误把人踹去登录页 |
| name 姓名 | ✅ 可改（PATCH /api/auth/profile） | ✅ | 姓名属人事信息，但改错字 / 补英文名是最常见的自助诉求。审计日志写入时已快照 `AuditLog.actorName`，本人改名**不会追溯改写历史留痕**；角色与部门仍然不可自改 |
| role 角色 | ❌ | ✅（护栏：不能改自己、不能去掉最后一个管理员） | 角色是权限本身，自改即自我提权 |
| departmentId 部门 | ❌ | ✅（调岗） | **它是鉴权输入**：dept 档页面按"用户的 departmentId ∈ 页面授权部门"放行，本人可改等于自己给自己发别的部门页面的阅读权 |
| email 登录身份 | ❌ | ❌（本期不开放） | 唯一键，登录与审计的身份锚点；改邮箱需要重新验证，留给后续版本 |
| active 停用 | ❌ | ✅（即离职处理） | 停用即全会话失效（`sessionVersion` 自增 + 缓存失效）；尽量不删除用户，页面外键也会拦住有作品的人。审计日志有 `actorName` 快照，即使删除，历史记录仍可读 |

关于**部门调岗**（原「方案边界与遗留」待明确项）：调岗只改 `User.departmentId`，
效果是**该员工的访问权立即随人变化**（这正是调岗的意义），但他名下已发布页面的
`deptDeps` 授权（PageDept，显式配置）**不自动跟随**——页面可能本来就有意共享给多个
部门，静默改动等于替人做业务决定；`Page.departmentId`（归属，统计口径）保留历史
快照不重写。调岗操作时管理员界面会提示核对名下的部门可见页面（已在「用户管理」页实现）。

## 八、上传安全

| 防护 | 说明 |
|---|---|
| 路径穿越 | 拒绝 `../`、绝对路径、盘符前缀，解压后再校验解析后的绝对路径仍在目标目录内 |
| 符号链接 | 拒绝 zip 中的符号链接条目 |
| Zip Bomb | 文件数 ≤500、单文件 ≤50MB、解压后总量 ≤200MB，且**按实际写入字节数二次校验**，不信任 zip 声明的大小 |
| 文件类型 | 扩展名白名单（html/css/js/图片/字体/媒体），拒绝 exe、php、sh 等 |
| 入口归一 | 单文件与 zip 统一落成 `{version}/index.html`，分发层只有一套逻辑 |
| 单一顶层目录 | zip 内若只有一个顶层目录且含 index.html，自动扁平化（**资源子目录一并保留**），避免 URL 多一层 |

## 九、部署拓扑

```
                    ┌──────── 内网 ────────┐        ┌──── 公网 ────┐
                    │ intranet.corp.example │        │ www.corp.example │
   内网用户 ─────────▶│ admin.corp.example   │        │   （匿名）    │
   （需登录）          └──────────┬───────────┘        └───────┬────────┘
                                │                          │
                    ┌───────────▼──────────────────────────▼────────┐
                    │  docker compose                                │
                    │  ├── db          mysql（仅内网网络可达）       │
                    │  ├── api         nestjs，挂载 data 全量        │
                    │  ├── web-internal  nginx，挂载 data 全量       │
                    │  └── web-external  nginx，仅挂载 data/public   │
                    └────────────────────────────────────────────────┘
```

为什么后台和内容要分两个域名：

`admin` 与 `intranet` 同域时，内容页里的 JS 可以 `fetch('/api/manage/pages')` 带着 Cookie 调用管理接口。分域后：

- 请求不带后台 Cookie（Cookie 是 host-only）
- 跨域请求被 CORS 预检拦截
- 双重保护

为什么不用宝塔 / K8s：

- 百人规模，单机 Docker Compose 是最合适的形态，K8s 是杀鸡用牛刀
- 免运维：一个 `deploy.sh` 完成全部流程
- 不引入宝塔这类面板，减少一层不透明的运维依赖

## 十、方案边界与遗留

| 项 | 说明 |
|---|---|
| **"停止乱建"无法技术强制** | 平台管不住员工自己写 HTML 存共享盘。平台能做的是：统一入口足够好用 + 提供使用统计让管理层看见谁在乱建、哪些页面没人用。**这部分需要制度配合，建议提前和领导对齐预期**，否则上线后容易被认为"平台没用" |
| 内网域名 DNS 泄露 | 架构已不依赖 DNS 隔离，但上线前仍建议核查内网域名未在公网 DNS 解析，作为纵深防御 |
| 站点身份的判定依据 | **已在代码侧修复**：原实现直接采信 `Host` / `X-Forwarded-Host`，外网伪造内网域名即可把管理接口从 404 变成 401（详见「防线 2 的前提」）。现已由「入口绑定 + 代理钉死 + 安全兜底」三重保证，并加了永久断言（隔离验收第 18 节） |
| 公网入口的网络隔离 | **代码管不了，必须做在网络层**：内网站点绑内网地址、只映射外网端口、其余入站关闭。Compose 预留了 `INTERNAL_BIND` / `EXTERNAL_BIND`，`INTERNAL_BIND` 默认 `127.0.0.1`（失败关闭），**上线时必须改成内网网卡地址**，否则内网访问不到；若改回 `0.0.0.0`，有公网 IP 的机器上会导致内网门户暴露。核查清单见部署手册 3.8 |
| ICP 备案 | 中国大陆服务器对外提供服务必须完成 ICP 备案，否则 80/443 会被拦。Demo 阶段用 IP + 端口规避 |
| 内容安全扫描 | P0 不含病毒 / 违规内容检测，生产建议接入扫描服务并提供举报下线入口 |
| SSO 对接 | 当前用平台自建账号，接口层已预留，接 AD / LDAP / 企业微信 / 钉钉 / 飞书属于 P2 |
| 部门调岗 | **已实现**：仅管理员可在「用户管理」调整；访问权随人立即变化，页面授权不自动跟随，编辑部门时界面弹出核对提示（详见「七、数据模型」的账号字段矩阵） |
| 管理员用户管理 | **已实现**（见下方「用户管理与账号自助」）：开号 / 改角色 / 调岗 / 启停 / 重置密码 / 受限删除全部有界面，接口在 `/api/manage/users` |
| 邮箱不可自助修改 | 唯一键 + 登录身份锚点，本期本人只读，管理员界面也不开放；改邮箱需要重新验证，留给后续版本 |
| 会话失效的粒度 | `sessionVersion` 让「停用 / 重置密码 / 本人改密」能立刻踢掉旧会话；**改角色、改部门不踢会话**（只清 60 秒缓存，下一次请求即按新权限判定）。这是有意为之：调岗不该把人从正在看的页面上弹出去 |
| 最后一个管理员护栏是防御性冗余 | 操作者本身必须是管理员，"降级 / 停用最后一个管理员"在当前角色模型下已被"不能改自己 / 不能停用自己"覆盖；保留这条是为了将来接系统操作、批量导入时不会把系统锁死 |
| 页面复审下线 | 领导有此诉求，但与"尽快跑通"的优先级冲突，放在 P1 |
| 资源令牌的 7 天有效期 | 打开后的页面地址形如 `/p/{slug}/_a/{令牌}/`，令牌 7 天有效。超过 7 天再打开旧书签：HTML 仍能看（会话有效），但图片会 403，从门户重新点一次即恢复。若要永久有效的链接，可把令牌改成跟版本号绑定（当前不做，避免产生长期可转发的资源凭证） |

### 用户管理与账号自助（已实现）

**为什么需要**：角色是审核发布权限的来源，账号没有管理入口，开号 / 离职 / 调岗就只能改 seed 或直接动数据库，百人内网上线后不现实。

**形态**：

- 管理员：独立导航项「用户管理」（`nav: true` · `roles: ADMIN` · `order: 75`，位于「审计日志」与「基础配置」之间）。账号与权限不是"配置"，需要全宽表格与筛选，塞进「基础配置」的两栏卡片布局不合适。
- 所有人：独立导航项「我的账号」（`order: 90`，侧边栏最底部）。员工侧导航因此从 3 项变 4 项（页面门户 / 我的页面 / 上传页面 / 我的账号），管理员侧 10 项。
- 右上角头像下拉保留「我的账号」（跳页面）与「修改密码」（弹窗），两者共用同一个 `PasswordChangeForm` 组件，不写两套校验。

**接口**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/manage/users` | 列表：`q` / `role` / `departmentId` / `active`（`true`/`false`/`all`，默认全部）/ `page` / `pageSize`；返回 `departmentName`、`pageCount`（含回收站） |
| POST | `/api/manage/users` | 新增：email（唯一 + 格式校验）、name、role、departmentId?；**初始密码由服务端生成**（12 位、剔除 `0O1lI` 等易混字符），只在本次响应出现一次 |
| PATCH | `/api/manage/users/:id` | 改姓名 / 角色 / 部门，审计 detail 记 `changes: { 字段: { from, to } }` |
| POST | `/api/manage/users/:id/active` | 启用 / 停用；停用同时 `sessionVersion++` |
| POST | `/api/manage/users/:id/reset-password` | 重置密码（服务端生成，一次性返回；审计绝不记录内容） |
| DELETE | `/api/manage/users/:id` | 受限删除：必须已停用 + 名下 0 页面（含回收站）+ 非自己 |
| PATCH | `/api/auth/profile` | 本人改姓名（唯一开放给本人的字段） |

**为什么放在 `/api/manage`**：用户是业务实体，不是 `categories` / `departments` 那类参考数据，所以从旧的只读 `GET /api/meta/users` 搬到 `/api/manage/users`，与 `/api/manage/pages` 同一命名域。`@AllowManage()` 让外网站点整体 404，`@Roles(Admin)` 让员工 403。

**五条护栏**（服务端强制，前端只做提示与置灰）：

1. 不能修改**自己**的角色
2. 不能停用 / 删除**自己**
3. 不能把**最后一个启用中的管理员**降级或停用
4. **任何用户字段变更都必须清掉该用户的会话缓存**——`SessionCacheService` 有 60 秒缓存，不清会出现"已停用仍能用旧 cookie 访问"的授权滞后窗口。**只有停用与重置密码才自增 `sessionVersion`**；改角色 / 部门只清缓存，下一次请求立即按新权限判定但不把人踢下线
5. **删除必须有前置条件**（已停用 + 名下无页面）：`Page.ownerId` 是必填外键，硬删会破坏数据

**审计动作**：`user_create`、`user_update`（含启停）、`user_reset_password`、`user_delete`、`profile_update`。detail 只记字段前后值与目标邮箱，**任何密码明文都不落库、不进日志**。

**为什么本人可以改姓名**（对原规则的修正）：原规则把姓名锁死，理由是审计日志的操作人显示名是实时 join 的，本人改名会追溯改写历史留痕。现在审计写入时快照 `AuditLog.actorName`，读取时取 `actorName ?? 实时 join ?? '系统'`，旧数据（快照为 null）自动回落到原行为——留痕不再受影响，于是把姓名开放给本人。顺带修掉了"用户被删除后其历史日志全变系统"的老问题。

**已知边界**：

- 姓名为空 / 超 40 字被拒；邮箱重复 / 格式错误 / 非法角色由 DTO 校验拦截。
- 重置密码后需要管理员把一次性密码转达本人；弹窗关闭后无法再查看，只能再次重置。
- 升级到本版本后，所有升级前签发的 cookie（JWT 不含 `sv`）会失效，**全员需要重新登录一次**。

**验收**：隔离验收第 19 节覆盖建号 / 初始密码登录 / 重复邮箱 / 坏邮箱 / 非法角色 / 三条自我护栏 / 姓名快照 / 重置密码 / 旧会话立即失效 / 角色变更立即生效 / 启停 / 受限删除 / 审计不含密码，共 45 条断言。
